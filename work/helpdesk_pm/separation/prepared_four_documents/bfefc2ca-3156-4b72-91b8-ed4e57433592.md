# 프로젝트 운영 규칙 · GitHub / Linear / 팀 대화

## 협업 도구

* Linear: 작업·마감·선행 관계·검증·결정 기록.
* GitHub: 실제 코드·브랜치·PR·리뷰.
* 기존 팀 대화 채널: 빠른 질문·도움 요청·작업 공유. 채널 개설·초대·메시지 전송을 완료했다는 기록은 아니다.

## 상태와 작업 선택

* Backlog: 배정 또는 시작 대기.
* Todo: 이번에 착수할 작업. 현재 T01\~T07.
* In Progress: 실제 작업 시작.
* In Review: 결과물/PR 검토와 통합 재현 대기.
* Done: 완료 기준, 관련자 검토, 통합 재현 확인 후.
* 막힘: 별도 상태를 새로 만들지 않고 선행 차단 관계와 이슈 본문에 필요한 도움 기록.

한 사람의 핵심 진행 작업은 1개를 원칙으로 한다. A는 팀장 도형준으로 확정했으며, B\~E 실명과 가용 시간은 T01에서 확인한다. 코드 작성이나 고정 예시 화면만으로 Done으로 바꾸지 않는다.

## Git 브랜치와 PR

기존 도서관 프로젝트의 방식을 새 저장소에 적용한다. 저장소와 기본 브랜치 개설은 T01에서 결정·실행한다.

* main: 발표·배포 가능한 안정 버전.
* develop: 팀 작업 통합.
* feature/NONONO-번호-짧은설명 또는 fix/NONONO-번호-짧은설명에서 작업.
* feature/fix → develop PR, 통합 검증 후 develop → main PR.
* PR 제목에 \[ADE-번호\] 표시.
* 관련 담당자 1명 이상 확인 후 병합. main 직접 변경 금지.
* 실행 방법·의존성·모델/설정 변경도 함께 기록.

## 작업 공유와 회의

작업한 날에 완료한 ID와 확인 결과 / 다음 작업 / 막힌 점·도움을 짧게 공유한다. 해결이 2시간 이상 지연되거나 기한 지연이 예상되면 당일 A에게 공유한다.

매주 화요일 11/3·10·17·24·12/1에 20분 통합 점검. 실제 회의 시각은 T01에서 합의한다. 화면 10분 → 의존성 5분 → 다음 완료 조건·담당자 5분. 실시 전에는 회의 결과를 기록하지 않는다.

“80% 완료” 대신 실제 실행 입력·결과·PR·링크를 제시한다. 실제 AI 호출·배포와 고정 예시/영상은 구분한다.

## 일정과 범위 변경

변경 이유·추가 작업·영향 모듈·필요 시간을 적고 A가 관련자와 검토한다. 같은 양의 일을 줄일 수 있을 때만 계획에 넣는다. 11/24 기능 동결 이후에는 결함 수정만 한다.

Jev 무료 실제 호출이 10/30까지 확인되지 않으면 B가 Gemini 분류로 대체한다. Gemini 무료 호출 자체가 불가하면 A가 교수와 허용 대안을 확인한다. 결제수단 연결로 해결하지 않는다.

## 결함과 주간 성과 기록

결함: 이슈 ID / 버전 / 가상 입력 / 기대 / 실제 / 재현 순서 / 담당 / 수정·재검증일.
P0: 키·개인정보 노출·결제 조건 위반. P1: 필수 흐름 중단·검토 누락·근거 없는 단정. P0/P1 최종 0건, P2는 영향·대응 기록.

주간 기록: 이번 주 목표 / 실제 완료 / 증거·검증 / 문제와 해결 / 다음 작업. 확인하지 않은 일을 완료 성과로 쓰지 않는다.
