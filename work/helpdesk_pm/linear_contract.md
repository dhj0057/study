# 공통 개발 계약과 검증 기준

이 문서는 AI Smart Help Desk의 분류·답변·공통 처리·화면 담당자가 같은 기준으로 개발하기 위한 실행 계약이다. 아래 함수와 데이터는 **구현할 계약**이며, 실제 API 호출·배포·성능 검증을 완료했다는 뜻이 아니다. Jev와 Gemini의 사용 가능 여부와 실제 엔진·버전은 기술 검증 후 기록한다.

## 1 모듈 사이의 책임

- **B 분류**: `classify(message) → Decision`. 문의 원문을 받아 분야·긴급도·검토 여부 또는 표준 오류를 반환한다. Jev와 Gemini 대체 분류 모두 같은 형식을 사용한다.
- **C FAQ와 답변**: `build_reply(message, decision, faqs) → Reply`. 관련 FAQ 번호와 안내문을 반환한다. 근거가 없으면 답변을 지어내지 않고 검토 안내를 반환한다.
- **A 공통 처리**: `create/get/list/update/retry_ticket → Ticket`. 접수·저장·부서 연결·검토 규칙·상태 변경·재시도를 담당한다.
- **D 화면**: 공통 처리 결과로 입력·조회·수정 화면을 구성한다. 모델 API를 화면에서 직접 호출하지 않는다.
- **E 검증**: 구현자와 합의한 정답·오류 조건으로 통합판을 재현하고 결과와 결함을 기록한다.

모델의 원본 응답은 B·C가 공통 형식으로 변환한다. 허용되지 않은 값이나 누락 필드는 정상 결과로 채우지 않고 형식 오류로 전달한다. 함수 이름과 상세 인자는 공통 계약 확정 때 조정할 수 있으나, 화면과 저장소가 같은 결과를 읽는 원칙은 유지한다.

## 2 공통 접수 데이터

| 필드 | 값과 규칙 |
| --- | --- |
| `ticket_id` / `message` | 고유 접수번호와 원문. 원문을 먼저 저장하며 재시도에도 번호를 유지한다. |
| `category` | `SCHOLARSHIP`, `ACADEMIC`, `FACILITY`, `OTHER`. 모호하여 판단을 보류하거나 분류가 실패하면 `null`을 허용한다. |
| `department` | A가 관리하는 분야별 매핑을 적용한다. 판단 보류·분류 실패는 `UNASSIGNED`로 표시한다. 실제 기관에 자동 배정하지 않는다. |
| `urgency` | `LOW`, `MEDIUM`, `HIGH`, `UNKNOWN`. `UNKNOWN`은 낮음이 아니라 미판정이다. |
| `review_required` | 불리언. 개인별 확인·모호함·FAQ 없음·`HIGH`·오류는 서비스 규칙으로 `true`가 된다. |
| `faq_ids` / `reply` | 근거 FAQ 번호 목록과 안내문. 근거가 없으면 빈 목록과 검토 안내를 사용한다. |
| `status` | `NEW`, `IN_REVIEW`, `DONE`. 화면에는 접수·검토 중·완료로 표시한다. |
| `resolution_note` | 관리자의 처리 메모. 완료 조건에서 `reply`와 함께 확인한다. |
| `error_code` / `engine` | 오류 없음 또는 분류·생성·형식 오류. 실제 모델명·버전은 설정과 검증 기록에 남긴다. |

모호한 문의의 `null / UNASSIGNED`는 합의된 판단 보류 결과가 될 수 있다. API 실패와 같은 뜻으로 취급하지 않으며, 둘 다 검토는 필수다. 분야를 수정하면 담당 부서와 FAQ 근거도 다시 확인한다.

## 3 안내와 검토 및 상태 전이

관련 FAQ가 있는 일반 절차 문의만 자동 안내한다. 개인별 접수·승인 결과를 묻거나 근거가 없으면 검토로 전환한다. `HIGH`는 안내 가능 여부와 관계없이 우선 확인 대상으로 표시한다. 오류나 미판정을 `OTHER / LOW`로 바꾸어 정상 처리처럼 보이게 해서는 안 된다.

모든 접수는 `NEW`에서 시작한다. 검토 대기는 `NEW + review_required=true`로 표현할 수 있으며, 관리자가 검토를 시작하면 `IN_REVIEW`, 확인을 마치면 `DONE`으로 변경한다. 자동 안내 생성이나 모델의 판단만으로 `DONE`을 만들지 않는다.

완료 요청 시 공백을 제외한 **최종 답변과 처리 메모가 모두 비어 있으면 차단**한다. 둘 중 하나가 있어도 관리자의 확인과 완료 요청이 필요하다. 완료된 문의는 읽기 전용이며 수정·재시도·재개 기능은 제공하지 않는다.

분류·생성 실패 후에도 접수번호와 원문은 남긴다. 실패 사유와 재시도를 안내하고 검토 필수로 표시한다. 재시도는 같은 접수번호의 결과를 갱신하며, 연속 클릭으로 중복 접수나 중복 갱신이 발생하지 않게 한다. 원본 인증 응답·키는 화면과 로그에 노출하지 않는다.

## 4 저장과 개발용 예시

A가 서버 메모리의 공통 저장소와 동시 갱신 보호를 맡는다. 사용자 창과 관리자 창은 같은 저장소를 조회하고 새로고침으로 최신 상태를 읽는다. 세션별 상태만 문의 원장으로 사용하지 않는다. 재시작 시 초기화되는 데모이며 장기 저장과 운영 권한 체계는 범위에서 제외한다.

B·C·D는 고정 예시로 먼저 병렬 개발할 수 있다. 이 단계는 화면에 개발용 예시임을 표시하고 실제 AI 호출과 구분한다. 실제 연결 증거에는 가상 입력·실행일·엔진·버전·키를 가린 결과를 남긴다. 고정 응답, 캡처 또는 영상만으로 실제 AI 동작을 완료했다고 보고하지 않는다.

## 5 가상 문의 30건과 측정 기준

E가 정답을 만들고 A·B·C가 확인한다. 기준본을 먼저 고정하고 변경 이유를 기록한다. 결과를 보고 정답을 바꾸어 성능을 높이지 않는다.

| 주된 유형 | 건수 | 기대 경로 |
| --- | ---: | --- |
| 일반 FAQ | 12 | 근거에 맞는 자동 안내 |
| 개인별 확인 | 6 | 검토, 실제 접수·승인 결과 단정 금지 |
| 모호한 문의 | 6 | 검토, 정답에 명시된 미분류·미배정 허용 |
| FAQ 근거 없음 | 6 | 검토, 없는 규정·날짜 생성 금지 |

합계 30건 중 검토 필수는 18건이며, **이 18건 안에 긴급 사례 6건을 포함**한다. 각 사례에 예상 분야·긴급도·부서·검토 여부·FAQ 번호를 기록한다. 개인정보 없는 가상 입력만 사용한다.

- 분야와 부서가 동시에 맞는 최초 결과 **24/30 이상은 개발 목표이며 현재 미검증**이다. 관리자 수정 전 결과로 계산하고 긴급도 일치 건수는 별도로 기록한다.
- 검토 필수 18/18과 긴급 사례 우선 확인 6/6은 통과 조건이다. 누락이 있으면 완료 판정을 보류한다.
- 일반 FAQ 12건은 선택된 근거 범위와 일치해야 하며, 없는 규정·개인별 결과를 단정한 사례는 0건이어야 한다.
- 실제 엔진·설정·버전·실행일·실패를 함께 남긴다. 30건은 기능 검증용이며 실제 학생 전체의 성능을 입증하지 않는다.

## 6 별도 오류 검증과 작업 완료

30건과 별도로 ① 빈 입력 차단 ② 분류 실패 시 접수 보존 ③ 생성 실패 시 검토 전환 ④ 허용되지 않은 분류값 차단 ⑤ FAQ 번호 불일치 차단 ⑥ 재시도·연속 클릭의 중복 방지 ⑦ 두 창의 조회·상태 갱신 ⑧ 완료 조건과 완료 문의 변경 차단을 재현한다. 시간 초과·한도 초과는 ②·③에 실패 응답을 주입해 확인한다.

Linear 작업의 Done과 문의 상태 `DONE`은 다르다. 작업은 관련 팀원 1명의 검토와 E 또는 확인자의 통합판 재현 후 완료로 옮긴다. 키·개인정보 노출·결제 조건 위반은 P0, 필수 흐름 중단·검토 누락·근거 없는 단정은 P1이며 최종 P0·P1은 0건이어야 한다. P2가 남으면 영향과 대응을 기록한다. 24/30 목표 미달은 범위와 한계를 조정하고 재검증하되 필수 검토 기준을 낮춰 통과시키지 않는다.
